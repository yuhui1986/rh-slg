## 二、架构文档评估

### 2.1 优势（做得好的地方）

**1) 结构完整、可追溯性强**

文档覆盖了从玩法分析→减法决策→技术选型→模块划分→子系统设计→性能预算→路线图→风险的完整链条。决策清单（D1–D20）每条都有结论和一句话理由，变更记录清晰（v1.0→v1.1→v1.2），这是工业级的架构文档水准。

**2) "灵魂机制"裁剪思路清晰**

§1.2 对《率土之滨》的拆解准确——铺路占地、战法搭配、大地图博弈、兵种克制、资源循环五条灵魂不可裁剪，其余按"为网游存在 vs 为乐趣存在"一刀切。这避免了 SLG 项目最常见的"什么都想要"陷阱。

**3) 核心层零引擎依赖是正确的架构赌注**

`slg-core` 不依赖 Bevy 的决策（D1、§3.2、§5.2 红线）是全项目最有价值的技术决策。Bevy 0.x 仍在快速迭代，破坏性变更多，隔离核心逻辑使：
- 战斗/寻路/生成可脱离引擎单测和基准
- 未来 Bevy 大版本升级成本局部化
- 更换渲染层成为可能（虽然概率低）

**4) 确定性纪律到位**

ChaCha12Rng + libm + 禁 HashMap 迭代序 + 种子战斗 + insta 快照测试，这一整套确定性工程实践对于需要战报回放和地图分享的 SLG 至关重要。文档不只是提了"要确定性"，还给出了具体技术方案。

**5) 编辑器共基座设计优雅**

"编辑器 = 游戏视图的超集"（§7.1）是一个成熟的设计模式（参考文明/魔兽编辑器），避免了两套渲染管线的维护噩梦。命令模式 + 撤销重做也是标准做法。

### 2.2 问题与风险

**P1 [高] 地图三种形态的转换接口未定义**

§6.1 定义了 MapDocument → Runtime World → Save 三种形态，但**没有定义转换函数签名**。这是实现时最容易出 bug 的地方：
- `load_map(doc: MapDocument) -> World` 的具体步骤？Chunk 如何从 RLE 密集数组展开为定长数组？
- `save_world(world: &World, map_hash: SHA256) -> SaveFile` 如何计算 tile_delta？
- 编辑器模式下 MapDocument 和 Runtime World 如何同步？双缓冲？实时写穿？

**建议**：在 §6.1 或 §6.2 补充转换函数的伪代码签名和同步策略。

**P2 [高] Bevy ECS 与游戏状态的映射策略过于模糊**

D14 说"运行时状态全在 Bevy World"，但没有回答关键问题：
- Tile 数据放 Component 还是 Resource？32×32 Chunk 内的 tile 是 Component 数组还是 Resource 内的定长数组？
- 武将/部队是 ECS Entity + Component 还是 Resource 内的 HashMap？
- 存档快照是 `World::serialize()` 还是手动序列化特定组件？

这些选择直接影响性能和代码复杂度。§6.1 说"只有城池/要塞等特殊格额外生成独立实体"，暗示大部分 tile 不是 ECS Entity，但没有明确说明数据到底放在哪。

**建议**：补充一个"ECS 数据映射表"，列出每种游戏对象的存储方式（Entity+Component / Resource / 混合）。

**P3 [中] AI 错峰决策的公平性问题**

§6.6 说"势力 i 在 tick%10==i 决策"，这意味着编号小的势力总是先决策。在同等信息下，先手 AI 可能抢占资源/地块。

**建议**：每局开始时随机分配势力编号到决策槽位，或用 `hash(tick, faction_id) % 10` 做伪随机错峰。

**P4 [中] 存档增量的 tile_delta 可能膨胀**

§10.3 存档只存 tile_delta（变更格），但如果一局打到后期，大部分格子都可能被占领/升级过，delta 可能接近全图大小，增量存档的轻量优势消失。

**建议**：补充"delta 合并"策略——当 delta 超过阈值（如全图 30%）时，做一次全量快照重置 delta。

**P5 [中] 程序化生成的性能目标激进**

§12.2 说"512² 地图生成 < 5s"，但生成管线（§8.1）包含 Simplex fBm 6-8 octave + Domain Warping + 河流后处理 + 泊松盘采样 + 模拟退火出生点。512×512 = 26 万格，每格需要 6-8 octave 噪声计算，5s 是一个有挑战性的目标。

**建议**：先做 benchmark 验证噪声生成的吞吐量；如果不够，考虑分层缓存（低分辨率噪声 → 上采样 → 局部细化）。

**P6 [低] 文档中多处引用格式不一致**

- §6.1 用"六边形 hex"，§7.1 用"cube 坐标 hex rounding"，D3 用"axial 坐标 (q,r)、pointy-top"——术语应统一
- §13 V1 占比之和 = 100%，但 T6（剧本）只有 5%，对于一个"三国鼎立"首发剧本来说偏少，实际可能需要 10%+
- D10 说"JPS 针对方格优化"但项目已改为六边形，JPS 在 hex 上的适用性存疑

**建议**：统一术语表；重新评估 T6 占比；D10 中 JPS 的 hex 适用性需要补充说明或删除。

**P7 [低] 缺少错误恢复/容错设计**

文档没有讨论：
- 存档损坏时的恢复策略（自动备份？回退到上一个自动存档？）
- 地图文件被篡改（hash 不匹配）时的具体处理流程
- 运行时 panic 的优雅降级（除了 crash log）

**建议**：在 §10 或 §11 补充容错设计。

## 四、Agent 团队评估

### 4.1 团队结构评估

**优势：**

1. **职责边界清晰**：每个 agent 有明确的 crate 归属和"禁止"清单。master-coordinator 不写代码只做调度，arch-guardian 不写业务只做审查，这种纪律性分工是团队协作的基础。

2. **派发表可执行**：master-coordinator 的派发表（§派发表）把任务类型→agent 的映射写得很清楚，跨 crate 拆卡的规则也明确了。

3. **验收标准具体**：每个 agent 的"完成标准"都是可验证的（cargo test、cargo clippy、proptest、insta 快照），不是空话。

4. **arch-guardian 的"红线巡检"机制好**：定期跑 `grep -r "bevy" crates/slg-core crates/slg-data` 检查核心层零依赖，这是自动化纪律。

**问题：**

**A1 [高] agent 之间缺少协作协议**

当前设计是"master-coordinator 派发 → agent 独立完成 → master-coordinator 验收"的单链路。但实际开发中频繁出现：
- core-engineer 改了 slg-data 的结构 → content-designer 的 RON 表需要同步 → editor-engineer 的容器格式需要同步
- render-engineer 需要 core-engineer 暴露一个新 API → 需要先协商接口

文档没有定义这种跨 agent 协作的流程。是通过 master-coordinator 中转？还是允许 agent 之间直接通信？

**建议**：在 master-coordinator.md 中补充"跨 agent 协作"流程——agent A 需要 agent B 的变更时，向 master-coordinator 提交"依赖请求"，由协调员协调优先级和顺序。

**A2 [高] 缺少"架构变更请求"的正式流程**

arch-guardian.md 说"确需架构变更时更新 ARCHITECTURE.md"，但没有定义谁可以发起变更请求、需要什么审批、变更影响如何通知其他 agent。

**建议**：定义 ACR（Architecture Change Request）流程：
1. 任何 agent 可以向 master-coordinator 提交 ACR
2. master-coordinator 评估影响范围，通知相关 agent
3. arch-guardian 评审并决定是否更新基线
4. 变更通知所有 agent

**A3 [中] content-designer 的定位偏弱**

content-designer 只负责 RON 数据表和文案，但实际上三国内容的设计（武将数值、战法平衡、剧本事件链）需要大量的游戏设计能力。agent 定义中没有提到设计方法论（如数值平衡的参考框架、事件叙事结构）。

**建议**：补充内容设计的方法论指导，如数值平衡的基准参考（率土原版数值范围）、事件链的叙事模板。

**A4 [中] qa-engineer 的"试玩验证"定义模糊**

qa-engineer 的职责中提到"每里程碑按玩法清单验证正确性与体验"，但"玩法清单"没有定义。谁来写这个清单？标准是什么？

**建议**：由 master-coordinator 在每个里程碑开始前定义"验收玩法清单"（如"M1 验收：生成 256² 地图 → 占领 10 个格子 → 触发战斗 → 查看战报 → 保存/加载 → 100 tick 无崩溃"），qa-engineer 按清单执行。

**A5 [低] 缺少"代码审查"角色**

arch-guardian 负责架构审查，但不负责代码质量审查（代码风格、性能反模式、逻辑错误）。当前的代码质量完全依赖 cargo clippy + cargo test 的自动化检查。

**建议**：可以在 master-coordinator 的验收环节增加"代码质量抽查"（随机读 3 个新文件，检查注释/命名/错误处理），或者让 qa-engineer 承担这部分职责。

## 五、可执行性评估

### 5.1 能否直接开工？

**结论：基本可以，但有几个前置工作需要完成。**

| 前置工作 | 优先级 | 说明 |
|---------|--------|------|
| 补充 ECS 数据映射表 | P0 | 不确定 tile/entity 放 Component 还是 Resource，无法写代码 |
| 补充地图三形态转换接口 | P0 | 不知道 load/save 的函数签名，无法设计数据流 |
| 确认 Bevy 具体版本 | P1 | D20 说"pin 最新稳定版"，但需要确认当前最新版的 API |
| 定义跨 agent 协作流程 | P1 | 多个 agent 同时开工时如何协调依赖 |
| 补充验收玩法清单模板 | P2 | qa-engineer 需要知道验什么 |

### 5.2 任务拆分合理性

V1 任务组（T1–T7）的拆分基本合理，但有几个建议：

1. **T1（工程骨架）应该拆得更细**：workspace 8 crate 的创建、CI 配置、tracing 日志、fluent i18n 是 4 个独立任务，应该可以并行
2. **T2（大地图）和 T3（核心玩法）有强依赖**：大地图的 Chunk 渲染需要 slg-core 的地图数据结构先定义好，建议 T3 的 map/ 模块先于 T2 启动
3. **T6（剧本）依赖 T3+T4+T5**：剧本需要战斗、AI、经济系统都就位才能测试，应该放在最后

建议的任务依赖图：
```
T1 工程骨架
 ├─→ T3 核心玩法（map/ 部分先启动）
 │    ├─→ T2 大地图渲染
 │    ├─→ T4 战斗系统
 │    └─→ T5 AI 系统
 │         └─→ T6 剧本
 └─→ T7 编辑器雏形（可与 T2/T3 并行，但依赖 T1 完成）
```

## 六、总体评价与建议

### 6.1 总体评价

这是一份**高质量的架构文档**，在以下方面做得很好：
- 玩法分析→技术决策的推导链完整
- 决策清单可追溯、可维护
- 确定性工程实践到位
- Agent 团队分工清晰

主要不足在于：
- ECS 数据映射和接口签名等实现细节缺失
- Agent 间协作流程未定义
- 个别技术决策需要补充验证（JPS hex 适用性、生成性能）

### 6.2 优先改进建议

| 优先级 | 改进项 | 工作量 |
|--------|--------|--------|
| P0 | 补充 ECS 数据映射表（tile/entity/resource 的存储方式） | 2h |
| P0 | 补充地图三形态转换接口伪代码 | 2h |
| P1 | 定义跨 agent 协作流程（ACR + 依赖请求） | 1h |
| P1 | 确认 Bevy 具体版本并 pin | 0.5h |
| P2 | 补充验收玩法清单模板 | 1h |
| P2 | 统一术语表（hex 坐标系相关） | 0.5h |
| P2 | 重新评估 T6（剧本）占比 | 0.5h |
| P3 | 补充容错设计（存档损坏/地图篡改） | 1h |

### 6.3 结论

**架构文档已达到可开工的基线水平**，P0 项建议在 M0 阶段（workspace 骨架搭建期间）由 arch-guardian 补充到 ARCHITECTURE.md 中，不影响整体推进节奏。Agent 团队设计合理，核心层零引擎依赖的架构赌注是正确的，确定性工程实践是全项目的技术亮点。

建议下一步：由 master-coordinator 启动 M0 剩余任务（workspace 骨架 + CI），同时 arch-guardian 补充 P0 项的接口定义。
